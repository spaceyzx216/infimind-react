## 问题 1（P0）：FTS5 不切分中文，词法索引大面积失效

**问题**

`unicode61` 分词器不会切分中文，连续的汉字串被当成**一个 token**，导致 MATCH 是"整 token 精确匹配"。36 个核心法律检索词的平均词汇召回率只有 **14.8%**：

| 检索词 | 实际包含该词的条款 | 现状 FTS 命中 | 召回率 |
| --- | --- | --- | --- |
| 付款 | 112 | **0** | 0% |
| 违约 | 329 | **0** | 0% |
| 主体 | 104 | **0** | 0% |
| 授权 | 105 | **0** | 0% |
| 质保 | 37 | **0** | 0% |
| 管辖 | 29 | **0** | 0% |
| 签收 | 43 | **0** | 0% |
| 标的 | 16 | **0** | 0% |
| 履行 | 132 | 3 | 2% |
| 交付 | 139 | 10 | 7% |
| 验收 | 139 | 13 | 9% |
| 违约金 | 154 | 21 | 14% |

**原因**

`clause_fts` / `risk_rule_fts` 建表时用的是 `tokenize='unicode61'`。该分词器按 Unicode 类别切分，把连续的 CJK 字符视为一个完整的"词"，只在标点和空白处断开。因此"甲方应于收到发票后付款"整句是一个 token，检索 `付款` 自然命中 0 条。

补充：`"付款"*`（前缀匹配）只能救到 36/112，因为检索词常常出现在 token 中间而非开头。

**修改方案**

采用**中文 2-gram 索引**：索引期把中文按相邻两字展开，查询期把检索词转成 bigram 短语。实测词汇召回率 **14.8% → 100%**。

选它而不选 jieba 的理由：法律文本大量使用词表外术语（"加速到期""价款税分离"），分词器会切碎；2-gram 无词表、零依赖、确定性。

`server/services/knowledge-processor.js` 新增两个纯函数：

```js
const CJK_ONLY = /^[\u4e00-\u9fff]+$/

/** 索引期：把中文按 2-gram 展开，使 unicode61 能正确切分中文。不改动入库原文。 */
export function toIndexText(text) {
  const tokens = String(text || '').match(/[\u4e00-\u9fff]+|[A-Za-z0-9]+/g) || []
  const out = []
  for (const token of tokens) {
    if (CJK_ONLY.test(token)) {
      if (token.length === 1) { out.push(token); continue }
      for (let i = 0; i < token.length - 1; i += 1) out.push(token.slice(i, i + 2))
    } else out.push(token.toLowerCase())
  }
  return out.join(' ')
}

/** 查询期：检索词转 bigram 短语；多 bigram 用短语查询保证相邻，等价于子串匹配。 */
export function toQueryTerm(term) {
  const clean = String(term || '').trim().replace(/"/g, '')
  if (!clean) return ''
  const parts = toIndexText(clean).split(' ').filter(Boolean)
  if (!parts.length) return ''
  return parts.length === 1 ? `"${parts[0]}"` : `"${parts.join(' ')}"`
}
```

`server/services/knowledge-base.js` 改两处：

```js
// ① 写 FTS 时用索引态文本（addTemplate 内，clause_fts 与 risk_rule_fts 都要改）
insertClauseFts.run(clauseId, contractType || '', referenceRole || 'reference',
  toIndexText(`${clause.clauseNo || ''} ${clause.title || ''} ${clause.parentTitle || ''}`.trim()),
  toIndexText(clause.content || ''))

// ② 查询构造改为 bigram 短语（buildFtsQuery 内）
function buildFtsQuery(query) {
  return String(query || '合同').trim().split(/\s*OR\s*|\s+/).filter(Boolean)
    .map(toQueryTerm).filter(Boolean).join(' OR ')
}
```

**注意**：FTS 里存的是索引态副本，改完必须执行 `npm run import:templates` 全量重建。建议同 PR 引入 `indexVersion`，启动时检测版本不一致即提示重建。

**不要用 trigram**：它要求至少 3 个字符，两字中文法律词命中率只有 19.4%，比现状还差。

## 问题 2（P0）：证据选择丢掉 56% 的可用类别覆盖

**问题**

分阶段归因显示，候选池本来能覆盖 0.762 的风险类别，但送进提示词的最终 10 条只剩 **0.3352**：

| 阶段 | 类别覆盖率 |
| --- | --- |
| 候选池 top-48 | 0.7623 |
| 重排后 | 0.7623（重排只是排列，不改变集合覆盖） |
| **最终 top-10** | **0.3352** |

**原因**

`diversifyEvidence()` 的三条规则共同造成这个结果：

1. **每文档硬上限 2 条** —— 单一模板会挤占名额；
2. **只给"结果里恰好出现的 topicLabels"保底 1 条 risk_rule** —— 而不是给"审查计划里的每个主题"保底。分词坏掉的时代很多主题直接空召回，于是连保底名额都不会被创建；
3. **最终 10 条里只有约 3.6 条是 risk_rule** —— 而评测口径只认 `category`，所以覆盖能力被进一步压缩。

**修改方案**

把"按文档限流"改为"**按审查主题分配名额**"：

```js
function diversifyEvidence(results, limit, topics = []) {
  const selected = []
  const perDocument = new Map()
  const PER_DOC_CAP = 3            // 从硬 2 条放宽到 3 条
  const add = (item) => {
    if (!item || selected.some((s) => s.evidenceId === item.evidenceId)) return false
    if ((perDocument.get(item.templateId) || 0) >= PER_DOC_CAP) return false
    selected.push(item)
    perDocument.set(item.templateId, (perDocument.get(item.templateId) || 0) + 1)
    return true
  }
  // 1) 保留原有意图：正向模板条款 1 条 + 风险反例规则 1 条
  add(results.find((i) => i.referenceRole === 'excellent_template' && i.kind === 'clause'))
  add(results.find((i) => i.referenceRole === 'annotated_case' && i.kind === 'risk_rule'))
  // 2) 关键改动：为"计划中的每个审查主题"保底 1 条 risk_rule
  for (const topic of topics) {
    if (selected.length >= limit) break
    add(results.find((i) => i.kind === 'risk_rule' && i.topicLabels?.includes(topic.label)))
  }
  // 3) 剩余名额按重排分数填充
  for (const item of results) { if (selected.length >= limit) break; add(item) }
  return selected.slice(0, limit)
}
```

调用点：`searchEvidence` 内已有 `topics`，直接传入 —— `diversifyEvidence(reranked, limit, topics)`。

**关键提醒**：这一条必须和问题 1 **同一个 PR 一起做**。实测单独修分词端到端反而**略降**（0.3352 → 0.3182）——因为召回变好后候选池塞满"相似但同质"的证据，旧选择策略吃不下来。两件一起做是 **0.3352 → 0.4815（+44%）**。

## 问题 3（P0）：条款证据无 category，无法参与风险维度覆盖

**问题**

`clauseRowToEvidence()` 返回的 `category` 是写死的空串 `''`，只有 `riskRowToEvidence()` 带真实类别。所以：

- 评测口径下**只有 risk_rule 能贡献类别覆盖**；
- `diversifyEvidence` 的"每主题保底 1 条 risk_rule"也无法用条款证据补位；
- 最终 10 条里 risk_rule 只占 0.36，覆盖能力被结构性限制。

**原因**

`template_clauses` 表**根本没有 category 字段**（只有 `clause_no / title / parent_title / content`），建表时就漏了；而 `risk_rules` 有。这是表结构缺失，不是映射 bug。

**修改方案**

1. `template_clauses` 增加 `category TEXT DEFAULT ''` 字段（沿用 `knowledge-base.js` 里已有的 `ALTER TABLE ... ADD COLUMN` 迁移写法）。
2. 在 `addTemplate` 写入条款时用现成的分类器推导：`inferRiskCategory(`${clause.title} ${clause.content}`)`（函数已在 `knowledge-processor.js`，13 类正则表）。
3. `clauseRowToEvidence()` 改为返回 `category: row.category || ''`。
4. 重建索引后，条款证据即可参与维度覆盖与主题保底。

## 问题 4（P0）：评测指标混合两层且不可复现，无法作为门禁

**问题**

- `meanCategoryRecall` 一个数字同时承载"检索质量"和"选择策略"两层信息，改动后无法判断是哪一层变好/变差；
- 41 个评测用例**全部来自已入库的坏例**，是"自己考自己"；
- 评测脚本会调用网络重排器，**同一份代码在不同时刻跑出 0.23~0.34 的不同结果**；
- 没有 CI 门禁，知识库改动无法验证。

**原因**

`server/scripts/evaluate-knowledge-base.js` 是为"一次性回归"设计的：只输出一个汇总指标，`RAG_EVALUATION_*` 控制 topK，且 `npm run evaluate:knowledge-base` 虽然强制了 `RAG_RERANKER_MODE=heuristic`，但脚本本身**不检测网络重排器是否被触发**，也不区分阶段。

**修改方案**

新增 `server/scripts/evaluate-retrieval-stages.js`，一次跑出四个分层指标：

```js
{
  indexRecall:            按条款 ID 的 Recall@48（纯本地、确定性）   // 索引+召回层
  poolCategoryRecall:     候选池的类别覆盖                        // 召回层
  selectedCategoryRecall: 最终上下文的类别覆盖                    // 选择层
  redundancy:             最终上下文里"同类别重复占比"             // 选择层
}
```

配套三条硬要求：

1. **评测必须离线**：脚本内断言"未发生网络降级"，一旦降级立即报错退出（而不是像现在只 `console.warn`）。
2. **补人工金标**：抽 30-50 条人工标注"这份合同该发现哪些风险"，作为 held-out 测试集。
3. **挂 CI 门禁**：知识库相关改动若 `selectedCategoryRecall` 下降即失败。

`server/scripts/evaluate-knowledge-base.js` 保留为兼容入口，内部改为调用新脚本。

## 问题 5（P1）：向量检索静默失效，"混合 RAG"名存实亡

**问题**

`.env.local` 里 `RAG_VECTOR_URL` 是配了的，但 Qdrant 服务没起，`searchVectorEvidence` 抛 `fetch failed` 后只打一条 `console.warn` 就跳过。实际跑的是**纯词法检索**，而且是没有向量的那一半——所谓"混合 RAG"只剩一个坏掉的单腿。

评测日志里每个用例都有一行：

```
[knowledge-base] Vector retrieval skipped: fetch failed
```

**原因**

`knowledge-base.js:232` 的捕获块只做 `console.warn`，既不上报指标也不影响健康检查状态，因此"向量挂了"在外部完全不可见。

**修改方案**

两条路选一条，**但无论选哪条都必须配降级告警**：

| 方案 | 优势 | 代价 | 建议 |
| --- | --- | --- | --- |
| **`sqlite-vec` 扩展** | 与 `better-sqlite3` 同栈、零额外运维、单文件、可直接 JOIN 现有表做结构化过滤 | 生态较新 | **MVP 推荐** |
| Qdrant（已有代码） | 成熟、可水平扩展、过滤能力强 | 多一个必须运维的服务，当前就是因为没起而失效 | Growth 期 |

```js
catch (error) {
  retrievalDegradations.inc({ kind: 'vector', reason: error.code || 'unknown' })
  logger.warn({ event: 'retrieval.degraded', kind: 'vector' }, error.message)
  // 不再只是 console.warn
}
```

`/api/knowledge-base/status` 增加 `degraded: true` 与最近降级原因。

## 问题 6（P1）：重排器限流后静默降级

**问题**

SiliconFlow 重排器返回 `429 TPM limit reached` 时，`rerankEvidence` 静默回落到启发式打分。也就是说：**你以为在跑 bge-reranker-v2-m3，实际在跑一个拍脑袋的线性公式**，而且没有任何痕迹。

实测中同一个配置连续两次运行分别得到 0.339 和 0.229。

**原因**

`evidence-reranker.js:32` 的 catch 块只 `console.warn` 后 `return heuristic`。同时 `heuristicRerank` 的权重（`retrievalScore * 100 + termMatches * 0.8 + focusMatches * 0.35 + roleBonus`）是手写的经验值，从未标定。

**修改方案**

1. 降级必须上报指标 + 结构化日志（同问题 5 的模式）。
2. **评测期禁止降级**：评测脚本断言未发生降级，否则报错退出——这是让评测可复现的前提。
3. **标定启发式权重**：用评测集对 `termMatches / focusMatches / roleBonus` 的系数做网格搜索，至少让 fallback 路径不是拍脑袋的。
4. 生产加限流保护：并发请求合并、结果缓存、失败计数超阈值时短期熔断（避免持续打满 TPM 配额）。

## 问题 7（P1）：FTS 异常回退到 LIKE 时取错了词

**问题**

`lexicalClauseSearch` / `lexicalRiskSearch` 在 FTS 查询抛错时，回退到 `LIKE '%第一个词%'`。而第一个词是 **topic 标签**（如 `价税、付款与发票`），几乎不可能在条款里逐字出现 —— 于是该主题**静默空召回**，且外部完全看不出发生了回退。

**原因**

```js
// knowledge-base.js:310
.all(`%${firstQueryTerm(query)}%`, ...)
```

`firstQueryTerm(query)` 取的是 `buildFtsQuery` 之前拼接串（`[topic.label, topic.query].join(' OR ')`）的第一个片段，也就是标签本身，而不是标签拆出的关键词。

**修改方案**

回退逻辑改为按 `topic.terms` 逐词 OR，而不是取第一个片段：

```js
// 回退时用主题词表而不是标签
const fallbackTerms = terms.filter(Boolean)
const likeClause = fallbackTerms.map(() => 'c.content LIKE ?').join(' OR ')
.all(...fallbackTerms.map((t) => `%${t}%`), ...)
```

同时：回退必须打日志 + 计数（属于降级，同问题 5）。

## 问题 8（P1）：FTS 列权重未启用，标题与正文等权

**问题**

`clause_fts` 有 4 列（`contract_type / reference_role / heading / content`）、`risk_rule_fts` 有 6 列，但查询用 `ORDER BY rank`，即 **BM25 默认全列等权**。命中标题里的"付款"和命中正文深处的"付款"得分一样。

**原因**

`ORDER BY rank` 是 FTS5 的默认排序，等价于 `bm25()` 无参调用，不给任何列加权。

**修改方案**

显式指定列权重，让标题与风险类别高于正文：

```sql
-- clause_fts: contract_type, reference_role, heading, content
ORDER BY bm25(clause_fts, 1.0, 1.0, 3.0, 1.0)

-- risk_rule_fts: contract_type, category, severity, trigger_text, risk_text, recommendation
ORDER BY bm25(risk_rule_fts, 1.0, 2.5, 1.0, 2.0, 1.5, 1.0)
```

权重值应通过问题 4 的分层评测标定，不要凭感觉定。

## 问题 9（P1）：severity 字段失效（83% 都是"中"）

**问题**

604 条风险规则中 **503 条是"中"（83%）**，只有 101 条是"高"，"低"一条都没有。这个字段目前既不能用于过滤、也不能用于排序或界面分级。

**原因**

`inferSeverity()` 只做关键词匹配：文本里出现"极高/特别高/高危/严重/重大"才升级为"高"，出现"中危/中等"才是"中"，**其余全部默认返回"中"**。而批注文本里本来就很少出现这些词，所以绝大多数落进默认值。

**修改方案**

废弃纯关键词推断，改为**可解释的三维打分**：

| 维度 | 说明 |
| --- | --- |
| 金额敞口 | 是否涉及无限责任、无上限赔偿、无期限延期付款 |
| 权利不对等程度 | 是否单方变更/单方解释/排除法定抗辩 |
| 法定强制条款 | 是否触及强制性规定（如排除法律适用、放弃法定解除权） |

三项加权得到 severity，再由离线模型对存量 604 条批量重标一次，人工抽检 10% 验证。**目标：让"高"的占比落在 15-25% 的合理区间**，而不是现在这个几乎恒定的值。

## 问题 10（P1）：trigger_text 存的是整条条款，不是触发片段

**问题**

`trigger_text` 无法用于精确定位与高亮，同时让 `risk_rule_fts` 的 `trigger_text` 列失去区分度（它与正文高度重合，BM25 无法区分）。

**原因**

代码写死了整条条款内容：

```js
// knowledge-processor.js:81
triggerText: (clause?.content || '').slice(0, 1000),
```

**修改方案**

从"整条条款"改为"**触发片段 + 字符偏移区间**"：

1. 先从批注文本里抽引号/加粗片段作为候选触发串；
2. 抽不到时，跑一次离线抽取任务，产出 `(start_offset, end_offset)`；
3. `risk_rules` 增加 `trigger_start` / `trigger_end` 字段；
4. 检索侧可据此做精确定位与前端高亮。

有偏移区间之后，问题 8 里 `trigger_text` 那一列的权重才有意义。

## 问题 11（P1）：无结构化过滤，只有合同类型一个条件

**问题**

召回只按 `contract_type` 过滤（词法走 SQL、向量走 payload filter），素材已有的 `reference_role`、`industry`、`source_path`、`pair_key` 等元数据全部没有参与过滤。结果是不相关合同类型的证据会挤进候选池。

**原因**

`searchEvidence` 只从 `reviewPlan.contractType` 取一个过滤条件，其余元数据仅作为字段透传，从未进入 WHERE 或向量 filter。

**修改方案**

建立**结构化元数据过滤层**，让过滤条件可组合：

| 字段 | 用途 |
| --- | --- |
| `contract_type` | 硬过滤（已有） |
| `reference_role` | 按任务模式过滤（只要正向范本 / 只要风险反例） |
| `industry` | 行业相近优先 |
| `region` / `effective_date` | 为劳动法规则、地方社保规则预留（见问题 18） |

两条召回路径（词法 / 向量）必须使用**同一套过滤条件**，避免结果口径不一致。

## 问题 12（P1）：现有风险类别词表未被反向用于查询扩展

**问题**

用户问"付款"，检索就只找"付款"两个字，不会带上"支付/结算/价款/发票/收款账户"。大量本应命中的条款因为用词不同而漏召回。

**原因**

`knowledge-processor.js` 里已经有一张高质量的**13 类风险类别 → 正则词表**（`inferRiskCategory`），但它只被用来"给文本归类"，从未被反向用于"扩展查询词"。

**修改方案**

把这张表反向用起来做**零成本查询扩展**：

```js
// 检索"付款" → 命中类别「价税、付款与发票」 → 并入该类的全部同义术语
const expansion = CATEGORY_TERMS[inferRiskCategory(term)] || []
const terms = [term, ...expansion.filter((t) => t !== term)]
```

对 `contractType` 也做同样处理（"买卖合同"→"买卖/采购/销售/购销"）。这是项目里**唯一一张人工整理过的高质量词表**，用起来性价比极高。

## 问题 13（P2）：配对资产（19 组好/坏例）被完全闲置

**问题**

素材是成对采集的，库内已有 **19 组 `(excellent_template, annotated_case)` 配对**（另有 18 份素材没有对照），`pair_key` 字段也已入库 —— 但**检索期完全没有用到它**。

**原因**

`pairKey` 只作为 evidence 的字段透传（`clauseRowToEvidence` / `riskRowToEvidence` 都带上了），既没有参与召回，也没有参与排序、提示词构造或评测。这是一份"存了但没花"的资产。

**修改方案**

这份配对语料是天然的监督信号，至少能做三件事：

| 用法 | 做法 | 收益 |
| --- | --- | --- |
| **差分挖掘风险规则** | 好版 vs 坏版按条款对齐 diff → 自动产出 `(问题原文 → 修订后原文)` 对 | 比现在用正则从批注里抽规则**可靠得多**。现在 `extractRiskRules` 依赖 `【风险批注N】` 标记，`annotation_count = 0` 的坏例完全抽不到规则 |
| **对比检索** | 召回时同时给"坏例原文 + 同配对好例的对应条款" | Agent 2 的 system prompt 第 4 条本来就要求"优秀模板仅作正向对照"，但当前检索**根本不保证召回到配对的那一份** |
| **自动扩容评测集** | 用配对生成"给定坏条款，正确模板是否被召回"的成对评测 | 指标比 `categoryRecall` 锐利得多，且不依赖人工标注 |

## 问题 14（P2）：604 条风险规则跨文档重复同质，无归并层

**问题**

604 条规则来自 41 个坏例，同一类风险在不同合同里各存一份。这直接造成候选池"**相似但高度同质**"——也是问题 2 里"召回变好反而指标变差"的深层原因。

**原因**

`risk_rules` 是**扁平结构**，每条规则独立挂在某个 `template_id` 下，没有任何跨文档的归并层。`UNIQUE(template_id, rule_key)` 只能防同一模板内重复，防不了跨模板。

**修改方案**

改为**两层结构**：

```
canonical_rule（规范规则，预计 80-150 条）
  ├─ 类别 / severity / 触发模式（正则或短语集）/ 修订方向
  └─ rule_instances[]  → 指向各原始实例（模板 + 条款 + 原文）
```

收益：召回不再依赖"恰好命中某个文档的某条规则"；类别覆盖成为**结构性保证**而非碰运气；severity 可以在规范层统一重估（配合问题 9）。

## 问题 15（P2）：短条款被直接丢弃

**问题**

`MIN_CLAUSE_CHARS = 80` 会把长度不足 80 字的条款直接过滤掉，导致定义条款、附件清单、签署页、短小的保密条款等内容**根本不入库**，检索永远找不到它们。

**原因**

```js
// knowledge-processor.js:51
const nonEmpty = expanded.filter((segment) => segment.content.length >= MIN_CLAUSE_CHARS)
return (nonEmpty.length ? nonEmpty : expanded).map(...)
```

只有"全部条款都短"时才会兜底保留全部；只要有一批长条款，短条款就被静默丢弃。

**修改方案**

1. 阈值从 80 降到 30；
2. 仍低于阈值的条款**合并到相邻条款**（而不是丢弃），合并后保留原 `clause_no` 作为 `parent_title`；
3. 在 `getKnowledgeBaseStatus()` 里暴露"被丢弃条款数"，让丢失可见。

## 问题 16（P2）：切分粒度太粗（条款级），一条含多个风险点

**问题**

一条 1400 字的条款作为一个检索单元，里面可能含 5 个独立风险点。检索命中后，整个条款被塞进提示词（再被 `slice(0, 1200)` 截断），**风险点被稀释**，且无法精确定位到具体句子。这是检索**精度**（区别于召回）的主要损失点。

**原因**

`splitIntoClauses` 只在"条款标题"层级切分，`MAX_CLAUSE_CHARS = 1600` 也只在超长时按段落机械拼接切分，没有语义粒度概念。

**修改方案**

在条款之下再切一层**原子义务单元**（"谁 / 在何时 / 做什么 / 不做的后果"）：

- 检索命中到义务级；
- 返回时带回所属条款作为上下文；
- 义务级单元同时是风险规则挂载的更精确锚点（配合问题 10 的偏移区间）。

现有 `template_clauses` 已有 `chunk_index` 字段，可复用为"条款内单元序号"。

## 问题 17（P2）：提示词侧硬截断证据

**问题**

`agent-2-review.js` 对证据做了两处硬截断：`evidence.slice(0, 12)` 和 `text.slice(0, 1200)`。这意味着：

- 即使检索层召回了 20 条有效证据，第 13 条起全部进不了模型；
- 一条 1400 字的条款被截到 1200 字，**截掉的往往正是风险所在的后半段**。

**原因**

```js
// prompts/agent-2-review.js:40,45
const evidenceSection = (evidence || []).slice(0, 12).map((item, index) => {
  ... 证据正文：${(item.text || '').slice(0, 1200)}
})
```

按"条数"和"字符数"硬性截断，而不是按 token 预算动态分配。

**修改方案**

1. 改为**按 token 预算分配**：给知识库证据划一个总预算，再按每条证据的 rerank 分数**加权分配**，高分证据给更多篇幅；
2. 截断时**优先保留命中位置附近的上下文**，而不是无脑保留前 1200 字；
3. 每条证据附带"为什么召回它"（主题 + 类别 + 分数），让模型知道证据的相关性等级，避免把低分证据当强依据。

## 问题 18（P1）：劳动合同内容严重不足，且评测完全未覆盖

**问题**

公司品牌是"**法飞飞—你的用工风险专家**"，`docs/prd.md` 的 Growth 阶段规划了 4 个劳动用工产品（劳动合同分析、劳动仲裁答辩、员工手册诊断、医疗期计算），但库里：

| 合同类型 | 文档 | 风险规则 |
| --- | --- | --- |
| **劳动合同** | **3** | **15** |

而且 **41 个评测用例全部来自商业合同坏例，完全没有覆盖劳动合同** —— 所以这个缺口在所有指标里都是隐形的，改了也不知道好坏。

**原因**

两个独立原因叠加：

1. **素材采集按"易得性"而非按产品矩阵排优先级** —— 素材目录 `法飞飞商务合同第一版20260705` 以商业合同为主；
2. **评测集只从已有坏例生成** —— `evaluation_cases` 在 `addTemplate` 里由 `reference_role === 'annotated_case'` 触发，没有坏例的产品线自然没有评测。

**修改方案**

1. **劳动用工知识独立建库**，不要混在"合同模板"里：
   - 劳动法规则库（国家 / 地方，带 `region` 与 `effective_date`）
   - 员工手册规范
   - 社保 / 医疗期计算规则（结构化规则表，不是文本）
2. **内容补齐优先级按 PRD 产品矩阵排**，不按素材易得性排；
3. **评测集必须先覆盖劳动合同** —— 在补内容之前就建立评测，否则无法验收。这是"先有尺子，再有材料"。

## 问题 20（P3）：无版本化与增量导入，只能全量重建

**问题**

目前只有 `resetKnowledgeBase()` 全量重建这一条路：`import-templates.js` 会先清空所有表再重新导入。这意味着：

- 无法增量补充素材（每次都要重跑 70 份文档的解析 + OCR + 向量同步）；
- 没有任何版本号，**任务无法记录"用了哪一版知识库"**；
- 出问题无法回滚；
- `content_hash` 字段已经在库里，但**从未用于查重**，重复素材可以静默入库。

**原因**

`import-templates.js` 是按"一次性建库"设计的：`resetKnowledgeBase()` → 全量 `addTemplate()`。没有版本表、没有增量比对、没有发布状态。

**修改方案**

1. **版本化**：引入 `kb_version`（内容版本 + 索引版本 + 提示词版本），任务记录实际使用的版本号。这直接对应 `docs/prd.md` 的 FR-019 / NFR-014。
2. **增量导入**：按 `content_hash` 比对，只处理新增与变更的素材。
3. **素材审核状态**：`draft / reviewed / published`，只有 `published` 参与检索。
4. **回滚能力**：按版本恢复，目标"发布事故 10 分钟内恢复上一稳定版本"（NFR-014）。
