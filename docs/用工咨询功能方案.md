## 一、更正说明：v3 的建议必须撤回

### 1.1 我上一轮错在哪

v3 里我推荐 `flk.npc.gov.cn`（国家法律法规数据库）的内部接口作为"永久免费方案"，理由是"三个端点全部实测跑通"。

**问题在于：我只验证了"技术上能不能调通"，没有验证"是否允许调用"。**

事后检查该站 `robots.txt`：

```
#禁止使用任何自动化工具、脚本、爬虫程序采集或复制网站数据
User-agent: *
Disallow: /
User-agent: *
Disallow: /private/
Disallow: /temp/
User-agent: BadBot
Disallow: /admin/
```

`User-agent: * / Disallow: /` = **全站禁止任何自动化访问**，并在注释里用中文明确写出"禁止使用任何自动化工具、脚本、爬虫程序采集或复制网站数据"。

**所以：技术上可行 ≠ 合规上可用。这个方案不能用于生产，正式撤回。**

（同时说明：v3 里对提示词三处法律事实的核实结论不受影响，那些是通过公开网页与官方发布内容交叉验证的。）

### 1.2 准确回答三个问题

| 问题 | 答案 |
| --- | --- |
| **现在官方接口是哪个？** | **没有官方接口。** 我用的 `flk.npc.gov.cn/law-search/*` 是该站**自己前端 SPA 调用的内部接口**，不是对外提供的 API |
| **官方是有 API 接口是吗？** | **不是。** 该站没有开放平台、没有开发者入口、没有 API 文档、没有 API Key 申请渠道；且 `robots.txt` 全站禁止自动化。它只提供**网页查询**，人工使用免费 |
| **是怎么接入的？** | 我从它前端的 JS bundle 里**逆向**出端点名与参数格式（`orderByParam` 必须是对象 `{"order":"-1","sort":""}`），再用 HTTP 直接调用。**技术可行，但违反 robots.txt，不可用于生产** |

虽然在生产上不可用，但这些实测结果对**人工核对法规**仍有价值，也印证了此前的事实修正：

## 二、正确方案：元典开放平台（法律 AI API + MCP）

### 2.1 这是什么

[元典开放平台](https://open.chineselaw.com/)（`open.chineselaw.com`）——**面向开发者的法律 AI API 与 MCP 工具平台**，提供法律法规、案例文书、企业信息、企业涉诉、**幻觉校验**等标准接口，并**支持 MCP Server 直接调用**。

- 有正规 API Key 鉴权
- 有接口文档、参数说明、多语言示例
- 接口标注 `freeAccessible: true`（**限时体验 / 免费可用**）
- 有真实调用量（语义检索接口累计调用 150 万+次）

**这才是"官方接口"问题应该得到的答案**——不是政府网站的内部接口，而是持牌的法律数据服务商提供的正规 API。

### 2.2 法律法规类接口

| 接口 | 价格（点） | 能力 |
| --- | --- | --- |
| **法律法规语义检索** | 15 | 自然语言 query → **法条级**语义检索；可按时效性、一级效力级别、地域、实施日期范围过滤 |
| **法条详情** | 1 | 单条法条详情；**可传 `refer_date` 按指定日期定位版本** |
| **法规详情** | — | 法规详情；**可传 `refer_date` 按指定日期定位当时有效版本** |

**语义检索的过滤能力**（这正是"检查确认"所需）：

| 过滤字段 | 可选值 |
| --- | --- |
| `sxx` **时效性** | 现行有效 / 失效 / 已被修改 / 部分失效 / 尚未生效 |
| `effect1` 一级效力级别 | 宪法 / 法律 / 司法解释 / 行政法规 / 监察法规 / 部门规章 / 党内法规 / 地方性法规 / 地方政府规章 / 地方规范性文件 …（共 17 类） |
| `dy` 地域 | 中央 + 31 个省市 |
| `law_start` / `law_end` | 法条生效日期范围 |

**返回字段**：`ftid` 法条 id、`fgid` 法规 id、`fgtitle` 法规名称、`num` 条号、`content` **正文**、`sxx` **时效性**、`effect1`/`effect2` 效力级别、`dy` 地域、`start`/`end` 实施与失效日期、`score` 相似度

> **`refer_date` 是超出预期的一个能力**：可以问"2024 年 3 月时这条法规是什么版本"。这正好对应提示词里"严格基于当前系统时间进行时效判定"，而且能处理**争议发生时间点的法律适用**问题（劳动法实务里很常见）。

### 2.3 MCP Server 接入

平台提供 5 个 Streamable HTTP MCP Server，鉴权用 `Authorization: Bearer YOUR_API_KEY`：

| Server | 用途 | 地址 |
| --- | --- | --- |
| `yuandian-law` | 法律法规 | `https://open.chineselaw.com/mcp/law/stream` |
| `yuandian-case` | 案例文书 | `https://open.chineselaw.com/mcp/case/stream` |
| `yuandian-company` | 企业信息 | `https://open.chineselaw.com/mcp/company/stream` |
| `yuandian-securities` | 证券合规 | `https://open.chineselaw.com/mcp/securities/stream` |
| **`yuandian-hallucination`** | **幻觉校验** | `https://open.chineselaw.com/mcp/hallucination/stream` |

另外提供统一 Skill：`$prc-legal-research`（统一路由法律法规/案例/企业/证券四类能力）。

npm 上还有 stdio 代理包：`yuandian-mcp-server@0.2.4`（"Stdio proxy for the YuanDian Streamable HTTP MCP server"）。

> **`yuandian-hallucination`（幻觉校验）值得重点关注**：它把"检查法规/案例是否真实存在"做成了独立服务。如果它能直接校验模型输出里的法条引用，就可以替代我们自建 `citation-verifier` 的相当一部分工作，直接满足原提示词里那条"确认该法规存在且现行有效时再引用"。

### 2.4 费用说明（需确认）

接口标注 `price`（如语义检索 15、法条详情 1）与 `assetType: POINT`，并标记 `freeAccessible: true`。

**需注册后确认的两件事**：
1. 「限时体验」的具体免费额度（次数 / 有效期）
2. 点数与人民币的兑换比例

**不要按猜测做预算**——先注册用免费额度跑通验证，再决定付费方案。

## 三、两条接入路线

| 路线 | 做法 | 评价 |
| --- | --- | --- |
| **A. REST API + 自研工具循环** | 后端直接调元典 REST 接口，用现有 `llm-client` 的工具循环 | ✅ **本项目推荐** |
| B. MCP Server | 后端做 MCP client 连元典的 Streamable HTTP MCP | 🟡 多一层依赖 |

**为什么推荐 A**：本项目的 LLM 是 **DeepSeek 的 Chat Completions**，它**不是 MCP client**——MCP 需要宿主（Claude Desktop、Cursor 这类）来承载。在本项目里要接 MCP，就得在后端再实现一个 MCP client，等于多加一层。而 REST + 自研工具循环与 `docs/` 里已设计的 `streamChatWithTools()` 完全一致，改动最小。

**MCP 路线的适用场景**：如果你后续要把这套能力给**别的支持 MCP 的宿主**（如 Claude Desktop、IDE）用，那 MCP 直接可用，无需改本项目代码。

### 4.2 执行器：失败回灌（防幻觉的关键）

```js
// server/tools/executor.js
export async function executeTool(name, args, ctx = {}) {
  const fn = EXECUTORS[name]
  if (!fn) return { error: `未知工具：${name}` }
  try {
    const result = await withTimeout(fn(args, ctx), 25000)
    auditToolCall({ name, args, ok: true, taskId: ctx.taskId })
    return result
  } catch (error) {
    auditToolCall({ name, args, ok: false, error: error.message, taskId: ctx.taskId })
    // 关键：失败回灌给模型而非抛异常 —— 模型会主动说"未能核实"，
    // 而不是静默退回凭记忆编造法条。
    return { error: `检索失败：${error.message}`, hint: '请在答复中说明该法规需人工核实，不要凭记忆引用' }
  }
}
```

### 4.3 `llm-client.js` 增加工具循环

```js
export async function* streamChatWithTools(systemPrompt, userMessage, {
  tools = [], executeTool, maxRounds = 4, onToolCall, ...options
}) {
  const messages = [{ role: 'system', content: systemPrompt }, { role: 'user', content: userMessage }]
  for (let round = 0; round < maxRounds; round += 1) {
    const response = await deepseekFetch('/chat/completions', { model: options.model, messages, tools, ... })
    const message = (await response.json()).choices[0].message
    if (!message.tool_calls?.length) { yield* streamFinal(message); return }
    messages.push(message)
    for (const call of message.tool_calls) {
      onToolCall?.(call.function.name, call.function.arguments)   // 前端展示"正在检索法规…"
      messages.push({ role: 'tool', tool_call_id: call.id,
                      content: JSON.stringify(await executeTool(call.function.name, JSON.parse(call.function.arguments || '{}'))) })
    }
  }
}
```

> 官方文档明确：Chat Completion **不支持在对话中间插入工具调用**，因此采用标准顺序循环。

### 11.2 修复：材料标题被误判为"未收录法规"

实测发现：模型分析上传材料时会用书名号引用**材料本身**（如《派遣员工劳动合同书》），

### 12.2 解析设计（`server/services/labor-book-parser.js`）

原文结构为「目录 + 正文」，含三类干扰：重复页眉、页码、跨页断句。三个关键设计：

**① 层级取自目录，不取自正文。**
正文里会引用法条原文，而法条本身也用「（一）（二）」编号。最初在正文里识别层级标题，
结果把答案从中间截断——产生了 25 字左右的残缺条目（如「……流程可以总结如下：」后面全丢）。
改为：先解析目录建立「问题 → 章/节/小节」映射，再按顺序贴回正文条目。
修复后最短条目从 25 字提升到 53 字，平均答案长度从 1073 字提升到 1430 字。

**② 正文只按【问题N】切分**，从根本上避免截断。

**③ 剥离重复页眉并按句末标点修复跨页断句。**
页眉插在句子中间会把「经济」切成「工经 / 济也」，使 2-gram 索引丢失该词——
必须拼接，否则检索会漏。

另外踩到一个坑：正文里存在页码换行的目录条目，与正文形态一致。
最初用「遇到第一个不带页码的问题行就停」判断目录结尾，
导致第二册只解析出 21 条目录记录（实际 218 条）。
改为「最后一个目录样式问题行之后即正文」后，五册目录/正文条目数完全对上。

## 十三、知识库检索效果评测

### 13.1 结论

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| **标题召回 Recall@1 / @10** | **89.0% / 98.4%** | 索引健康度（召回率上界） |
| **内容召回 Recall@1 / @10**（同主题） | **63.6% / 84.0%** | 用正文片段能否定位到正确主题 |
| **命中率 HitRate@5** | **90.0%** | 30 个真实提问中，27 个 top-5 至少含 1 条「相关」 |
| **精确率 Precision@5（相关）** | **26.0%** | top-5 判定为「直接相关」的比例 |
| **精确率（相关 + 部分相关）** | **64.0%** | 含相邻主题后的比例 |
| **首位相关率** | **46.7%** | top-1 即为「相关」的提问比例 |

> **注意口径**：召回率可由字符串比对确定；准确率（精确率）必须判断"检索结果是否真的回答了问题"，
> 属相关性判定，由 LLM 逐对判定得出（`deepseek-v4-flash`，30 题 × top-5 = 150 次判定）。
> 「相关」标准较严——要求条目直接讨论该问题；仅提供相邻背景的记为「部分相关」。

### 13.2 评测方法（`npm run evaluate:labor-kb`）

| 测试 | 方法 | 局限 |
| --- | --- | --- |
| ① 标题已知项 | 用条目自身标题当查询，看能否找回该条目 | 是召回率**上界**，标题词字面存在于索引中 |
| ② 内容片段 | 用答案正文片段（剔除标题用词）当查询 | 语料中同主题分散在多条，严格版会低估 |
| ② 宽松版 | 看 top-k 是否含**同章同节**条目 | 更贴近"是否定位到正确主题" |
| ③ 无 2-gram 对照 | 同一批数据建"修复前"索引跑同样查询 | 量化中文分词修复的收益 |

### 13.3 中文分词修复的量化收益

| 指标 | 无 2-gram（修复前） | 有 2-gram（现状） | 提升 |
| --- | --- | --- | --- |
| 标题 Recall@1 | 8.6% | **89.0%** | **+80.4pt** |
| 标题 Recall@10 | 16.5%～20.0% | **98.4%** | **+78pt** |

这是整个知识库最关键的工程改动：FTS5 的 `unicode61` 不切分中文，
整段汉字被当成一个 token，导致「付款」这类词命中 0 条。

### 13.4 本轮评测中发现并修复的 5 个缺陷

评测的价值不在于数字本身，而在于暴露问题。本轮共发现并修复：

| # | 缺陷 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | 关键词兜底逻辑对整句滑窗 | 产出「等特殊工」「条件下的」等碎片词，作为 OR 条件稀释有效术语 | 只在词典未覆盖区间取片段，且过滤首尾功能字与虚词 |
| 2 | 排序区分度不足 | 候选分数几乎并列（1.216 / 1.216 / 1.214），排序近似随机 | 改为「标题命中 IDF 加权和」，分数差距拉开（25.8 vs 18.4） |
| 3 | **忽略英文与数字检索词** | 「offer发出后反悔要赔多少」抽不出任何检索词，**返回 0 条结果** | 补入 ASCII 词抽取（Offer / N+1 / 2N 等） |
| 4 | **同义词表的键不参与匹配** | 「竞争对手」「取证」「业绩」既匹配不上词典，也就永远触发不了扩展 | 把同义词键并入匹配词表 |
| 5 | 大小写敏感匹配 | 标题写 `Offer`、用户写 `offer` → 匹配失败 | 打分时统一小写比对 |

另修 1 个评测脚本自身的 bug：`②宽松版`指标因 SQL 漏取 `chapter/section` 而恒为 0%。

**修复效果（同一批评测集）**：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 命中率 HitRate@5 | 62.1% | **90.0%** |
| 精确率 Precision@5（相关） | 17.2% | **26.0%** |
| 首位相关率 | 31.0% | **46.7%** |
| 未命中提问数 | 11 / 29 | **3 / 30** |

### 13.5 同义词扩展：本轮收益最大的改动

未命中的提问**多数不是"库里没有"，而是词表不匹配**：

| 用户口语 | 库里专业表述 | 修复后首位命中 |
| --- | --- | --- |
| 离职后去了**竞争对手**，怎么**取证** | 员工违反**竞业限制**，如何**调查取证** | ✅ |
| 员工**打架斗殴**解除 | 威胁、恐吓等**暴力**行为**违纪解除**败诉节点 | ✅ |
| **业绩不达标**为由解除 | 事先明确了**不胜任**的标准 | ✅ |
| 下班途中**交通事故** | **交通事故**责任无法认定，可以认定**工伤**吗 | ✅ |
| 公司**搬迁**导致**通勤**变远 | 企业**搬迁**，是**客观情况发生重大变化**吗 | ✅ |

实现要点：同义词键必须并入匹配词表（缺陷 4），且**扩展词权重 0.45 < 字面词 1.0**——
等权会稀释字面匹配的精度（实测标题召回从 89.7% 掉到 87.4%）。

### 13.6 剩余 3 个未命中（均为内容缺口，非检索缺陷）

| 提问 | 诊断 |
| --- | --- |
| 员工连续旷工三天，公司按严重违纪解除需要哪些证据 | 库内有「旷工1天扣3天工资」「病假未请假算旷工」等条目，但**没有"旷工→严重违纪解除"的组合条目** |
| 员工主动辞职，公司还需要支付经济补偿吗 | **库内确无该主题条目**（现有条目均为"特定情形下辞职可获补偿"） |
| 未签书面劳动合同，二倍工资最多支持几个月 | 库内有 4 条 2 倍工资条目，但**没有专门讲"最长支付期限"的**；top-3 已含「应签未签无固定期合同的2倍工资最长支付多久」 |

**这说明缺口在语料覆盖，不在检索。** 补齐方式：追加资料，或按 `--dump` 验证后补充同义词。

### 13.7 复现方式

```bash

npm run evaluate:labor-kb-precision    # LLM 相关性判定（准确率），会调用模型
npm run import:labor-books -- --dump "关键词"   # 单条查询核查
```

### 13.8 已知局限

1. **准确率的判定口径偏严**：「相关」要求条目直接讨论该问题；若把「部分相关」计入，
   精确率为 64.0%。对外表述时应说明口径。
2. **命中率 90% 是"至少一条相关"**，不代表 top-5 都可用——实际会作为证据整批送入提示词，
   掺杂的相邻条目可能干扰模型判断。下一步可考虑在送模型前做一轮相关性过滤。
3. **单轮评测未覆盖多轮对话**：用户追问、指代消解（"那这种情况怎么办"）时的检索效果未测。
4. 标题召回是**上界**，真实用户提问不会用条目标题的原词，应参考内容召回与命中率。

## 十四、检索策略详解与调优空间

### 14.1 当前搜索策略：单路词法检索 + 规则打分

**没有向量检索，没有模型重排。** 完整流程：

```
用户提问
  ↓ ① 查询解析  extractQueryTerms()
  { primary: 字面命中(词典最长匹配 + 英文词), expanded: 同义词扩展 }
  ↓ ② 双路召回（取并集）
  路A  FTS5（2-gram 短语查询）        LIMIT limit×6   → 生产 36 条
  路B  标题 LIKE 补齐（每词 limit×2，最多 8 词）
  ↓ ③ 过滤：标题/正文/章节路径全无检索词的候选直接丢弃
  ↓ ④ 规则打分
  score = 标题IDF加权和×1.0
        + 正文IDF加权和×0.35
        + FTS名次(RRF)×4
        + 含案号加成(+0.1/个，上限0.3)
  ↓ ⑤ 排序取 top-limit
```

### 14.2 查询改写：只有同义词扩展，没有 LLM 改写

| 能力 | 现状 |
| --- | --- |
| 同义词扩展 | ✅ 有（`SYNONYMS` 约 60 组，字面权重 1.0 / 扩展 0.45） |
| 英文/数字词抽取 | ✅ 有（Offer、N+1、2N 等） |
| 词典最长匹配 | ✅ 有（`LABOR_TERMS` 约 150 词 + 知识库标题/章节自动成词） |
| **LLM 查询改写** | ❌ **无** |
| 子问题拆分（复杂问题含多争点） | ❌ 无 |
| HyDE（假设文档嵌入） | ❌ 无 |
| 拼写纠错 / 繁简转换 | ❌ 无 |
| 多查询融合 | ❌ 无 |

### 14.4 截断位置调优（已量化）

| k | precision@k | hitrate@k | 送入模型的非相关条数 |
| --- | --- | --- | --- |
| 1 | 50.0% | 50.0% | 15 |

**结论**：k=5~6 是甜点区。降到 4 可少送 51 条噪声但命中率掉 10pt；

### 14.5 最小匹配度阈值：当前不可设

「相关」与「不相关」的分数分布**高度重叠**：

| 判定 | 样本数 | 最低分 | 中位分 | 最高分 |
| --- | --- | --- | --- | --- |
| 相关 | 56 | 1.7 | **8.9** | 28.8 |
| 部分相关 | 100 | 2.1 | 9.1 | 17.6 |
| 不相关 | 144 | 1.7 | **8.5** | 20.6 |

「相关」与「不相关」的中位分只差 **0.4**。任何阈值都会同时误杀相关条目：

| 阈值（丢弃最低 N%） | 保留相关 | **误杀相关** | 丢弃不相关 |
| --- | --- | --- | --- |
| 1.70（0%） | 56 | 0 | 0 |
| 6.41（10%） | 47 | **9** | 17 |
| 7.79（25%） | 41 | **15** | 44 |
| 8.89（50%） | 28 | **28（一半）** | 83 |

**根本原因：排序特征区分度不足。** 必须先提升区分度，阈值才有意义。

### 14.6 一次失败的调参（记录教训）

用离线调参器（取 30 条候选重排）测出「章节路径权重 0.25 + 标题覆盖率权重 3」
可将 precision@6 从 23.2% 提升到 25.0%，遂应用到生产——**实测反而降低**：

| 配置 | precision@6 | 内容召回@1 |
| --- | --- | --- |
| 路径 0 / 覆盖 0（**已回退为默认**） | **23.9%** | **55.2%** |
| 路径 0.25 / 覆盖 3 | 23.3% | 54.5% |
| 路径 0.5 / 覆盖 0 | 22.2% | 53.4% |

**原因**：离线调参用了 30 条候选（对应 FTS 池 `30×6=180` 条），而生产是
`limit×6=36` 条。**排序信号的效力随候选池大小变化**，宽池下的结论不可迁移。

两个权重已回退为 0 并在代码中留注释说明。**调参必须在生产候选池规模下跑真实评测。**

### 14.7 重排优化空间（按预期收益排序）

| 优先级 | 方向 | 说明 | 成本 |
| --- | --- | --- | --- |
| **P0** | **接入模型重排** | 合同知识库已有 `evidence-reranker.js`（SiliconFlow bge-reranker-v2-m3），labor KB 未接。粗排 36 条 → 精排 top-6。这是当前最大的单点提升机会 | 中（需处理该 reranker 的 429 静默降级问题） |
| **P0** | **送模型前做相关性过滤** | 当前 83.3% 命中率下，仍有约 1/3 送达条目不相关，会干扰模型判断 | 低 |
| P1 | LLM 查询改写 | 把口语问题改写成 2-3 个检索式，覆盖子争点 | 中（每题多一次模型调用） |
| P1 | 向量召回补一路 | 语义匹配可覆盖同义词表没穷尽的表述；需 embedding 服务 | 中高 |
| P2 | 排序特征增强 | 短语共现、检索词在标题中的位置、标题长度归一化 | 低 |
| P2 | 宿主编排改造 | 命中率 90% 但首位相关率仅 53%——可先让模型判断"检索结果是否够用"，不够则换检索式重查 | 高 |

### 14.8 关于「最大召回数量」的一个提醒

`KB_LIMIT=6` 是**送入模型**的条数；**候选池是 36 条**（`limit×6`）。
两者不要混淆：调 `KB_LIMIT` 影响的是送模型的证据量（14.4 有曲线），
调 `limit×6` 这个倍数影响的是重排的作用范围。当前倍数 6 未做过验证，
属于可优化项——候选池过小会让好的重排也无力回天。

## 十五、混合检索（语义+全文）与模型重排

### 15.1 新架构

```
用户提问
  ├─ 路① 词法召回  FTS5（2-gram 短语查询）+ 标题 LIKE 补齐   → 30 条
  ├─ 路② 语义召回  bge-m3 向量 + 暴力余弦（1024 维）        → 30 条
  │        └ RRF 融合 1/(60+rank) 两路求和
  │              └ 取融合 top 24 → 模型重排 bge-reranker-v2-m3
  │                    └ 阈值过滤（重排原始分 < 0.05 丢弃，保底 2 条）
  └─ 返回 top 6
```

**三路检索并行执行**（实务问答 / 合同知识库 / 案例库），耗时取最慢一路而非求和。

### 15.2 存储决策：不引入 Qdrant

向量以 BLOB 存于 `labor.db` 的 `labor_kb_embeddings` 表，进程内暴力余弦检索。
理由：语料 764 条 × 1024 维 ≈ 3 MB，暴力检索是 78 万次乘加，亚毫秒完成；
而 Qdrant 需要额外服务——**项目现状正是因为它没部署，导致合同知识库的向量路长期静默失效**（见 15.4）。
语料增长到数万条以上时再迁 Qdrant，接口不变。

向量按内容哈希判重，正文变更或换 embedding 模型后自动重建对应条目。

### 15.3 效果对比（30 题 LLM 判定 + 采样 120 条确定性评测）

| 指标 | 纯词法 | **混合 + 重排** | 提升 |
| --- | --- | --- | --- |
| precision@1 | 50.0% | **66.7%** | +16.7pt |
| precision@6 | 23.3% | **33.9%** | +10.6pt |
| hitrate@5 | 80.0% | **93.3%** | +13.3pt |
| hitrate@6 | 83.3% | **93.3%** | +10.0pt |
| 标题 Recall@1 | 89.0% | **99.2%** | +10.2pt |
| 标题 Recall@10 | 98.4% | **100.0%** | +1.6pt |
| 标题 MRR | 0.927 | **0.9958** | +0.069 |
| 内容 Recall@1（严格） | 55.2% | **76.9%** | +21.7pt |
| 内容 Recall@10（严格） | 73.8% | **92.3%** | +18.5pt |
| 内容 Top10 未命中 | 103 条 | **5 条** | −95% |
| 未命中提问（30 题） | 2 个 | **2 个** | — |

**典型案例**：原本纯词法失败的两个问题现已命中：

| 提问 | 纯词法首位 | 混合+重排首位 |
| --- | --- | --- |
| 员工连续旷工三天，按严重违纪解除需要哪些证据 | 员工提出辞职，单位在30天内按严重违纪解除可行吗？ | **出勤类违纪解除败诉节点与风险防范** |

### 15.4 顺带发现并修复的性能缺陷（影响合同审查链路）

**症状**：一次用工咨询耗时数分钟。

**逐路径计时定位**：

| 路径 | 修复前 | 修复后 |
| --- | --- | --- |
| 实务问答（混合+重排） | 711ms | 834ms |
| 合同知识库（第一路） | 642ms | 524ms |
| **合同知识库（跨类型）** | **120,495ms** | **524ms** |
| 案例检索 | 3ms | 3ms |

**根因**（`vector-store.js`，合同知识库共用）：

1. **`searchVectorEvidence` 先 embedding 再查 Qdrant** —— 而 Qdrant 从未部署，
   embedding 白做一遍并丢弃。用工咨询每次要跑两遍这条路。
2. **这些 `fetch` 全都没有超时**（`vector-store.js` 4 处 + `evidence-reranker.js` 1 处）。
   上游 5xx 或变慢时无限等待，实测单路径阻塞 **120 秒**。

**修复**：

| 修复 | 说明 |
| --- | --- |
| Qdrant 探活（30s 缓存，1.5s 超时） | 不可达即跳过向量路，不再浪费 embedding |
| 全部外部请求加超时 | 向量 8s / 探活 1.5s / 重排 8s |
| 三路检索并行 | 耗时取最慢一路而非求和 |

**效果**：单路径 **120,495ms → 524ms（230×）**；检索阶段 **120s+ → 1.2~1.5s**；
端到端 **数分钟 → 11.8~14.6s**。

> ⚠️ 这是**既有缺陷**：合同审查 `/api/contract-rewrite` 同样调用 `searchEvidence`，
> 在 Qdrant 未部署的环境下一直承担着这笔无效开销与阻塞风险。本次一并修复。

### 15.5 当前耗时构成与后续优化方向

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| 检索（并行三路） | 1.2~1.5s | ~9% |
| 模型生成 | ~13s | ~91% |

**现在的大头是模型生成，不是检索。** 若需进一步提速：

| 目标 | 手段 | 预期 |
| --- | --- | --- |
| 生成提速 | 减少 `maxTokens`、换更小模型、或前端更早渲染 | 数秒 |
| 检索提速 | 合同知识库两路（各 ~524ms）对用工咨询是次要信号，可设 1s 总预算或改为可选 | ~0.5s |
| 检索提速 | 缓存查询向量（相同/相似提问命中缓存） | ~0.3s |

### 15.6 降级可见机制（替代静默回落）

此前项目吃过两次亏：向量检索 `fetch failed`、重排器 429，都只打一行 `console.warn` 就静默回落，
导致"以为在跑混合检索，实际是坏掉的单路词法"持续数月无人察觉。

本次强制三件事：

1. 每次降级计入 `health` 计数器（`calls / ok / failed / degraded / lastError`）；
2. 结构化 warn，并区分原因（`rate_limit` / `network` / `auth` / `server`）；
3. **检索结果带 `retrieval` 元信息**，前端 `consult.start` 事件可见本轮真实模式：
   ```json
   { "mode": "hybrid+rerank", "lexical": {"count": 30}, "vector": {"count": 30, "degraded": false},
     "rerank": {"count": 24, "degraded": false}, "filteredByScore": 1, "elapsedMs": 723, "totalMs": 1370 }
   ```
   任一路降级会写入用户可见的 `warnings`，例如"语义召回（rate_limit）已降级，本轮按词法结果排序"。

`/api/labor/status` 暴露 `kb.search`，含向量覆盖率、provider 健康计数与全部可调参数。

### 15.7 最小匹配度阈值：现在可以设了

混合+重排后，「相关」与「不相关」的分数分布**分离度从 5% 提升到 44%**，
阈值调优从"不可行"变为"可行"：

**融合分（池内归一化）**：相关中位 0.9 / 部分相关 0.8 / 不相关 0.5

**重排原始分（绝对分，可跨查询比较）**：

| 阈值 | 保留条数 | precision | 误杀相关 | 滤掉不相关 | 相关保留率 |
| --- | --- | --- | --- | --- | --- |
| 0.05 | 272 | 27.2% | **2** | 20 | **97.4%** |
| 0.10 | 265 | 27.5% | 3 | 24 | 96.1% |
| 0.20 | 251 | 28.3% | 5 | 33 | 93.4% |
| 0.30 | 234 | 27.8% | 11 | 39 | 85.5% |
| 0.50 | 192 | **31.8%** | 15 | 59 | 80.3% |

**采用 0.05 作为安全下限**：几乎不损失相关（保留率 97.4%），同时减少送入模型的噪声。
带保底机制（至少保留 2 条），避免阈值把结果滤空。

> 对比：纯词法时代的阈值分析是"丢弃最低 25% 需误杀 15 条相关"，
> 根本不可用。分离度提升是阈值可行的前提。
