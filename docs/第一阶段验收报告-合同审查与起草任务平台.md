## 三、并发与串行约束验收

### 3.1 同对话串行（服务端硬约束）

对**同一 `threadId`** 连续提交两次审查任务：

| 提交次序 | HTTP 状态 | 响应 |
| --- | --- | --- |
| 第 1 次 | **202** | `{"taskId":"9afe4c59-...","status":"queued","threadId":"e2e-serial-1789721964309"}` |
| 第 2 次 | **409** | `{"error":"该对话已有审查任务正在处理，请先停止或等待其结束","code":"review_task_conflict"}` |

**结果：命中串行约束，返回 409 + `review_task_conflict`，符合设计。**

该约束由数据库**部分唯一索引**保证（而非前端 JS 判断），因此绕过前端直接调接口同样会被拦截：

- `idx_tasks_active_contract_draft_thread` —— 起草（冲突码 `draft_task_conflict`）
- `idx_tasks_active_contract_review_thread` —— 审查（冲突码 `review_task_conflict`）

索引条件：`user_id + thread_id`，且 `status IN (queued, running, retry_waiting, cancel_requested)`。

> **实现注意**：better-sqlite3 抛出的错误信息只带列名（`UNIQUE constraint failed: tasks.user_id, tasks.thread_id`），**不含索引名**，因此冲突判定必须按列名匹配。

### 3.2 不同对话可并行

不同 `threadId` 之间无约束，可同时排队执行；Worker 并发由 `TASK_WORKER_CONCURRENCY` 控制（本次为 1，串行消费）。

## 六、降级与边界

### 6.1 队列降级

`TASK_QUEUE_MODE` 支持三档：

| 模式 | 行为 |
| --- | --- |
| `bullmq` | 使用 Redis + BullMQ，支持多 Worker、任务重试与延迟调度 |
| `local` | 使用 SQLite 本地队列，无外部依赖，适合单机开发 |
| `auto` | 优先 BullMQ，Redis 不可用时自动降级为本地队列 |

当前配置为 `bullmq`（Redis 6380）。**降级为 `local` 时功能等价**，差异仅在于：

- 无跨进程 Worker，任务只在 API 进程内消费；
- 不享受 BullMQ 的重试退避与任务优先级；
- 进程重启后，排队中的任务依靠数据库状态恢复。

### 6.2 重试策略

- `max_attempts = 3`，失败后进入 `retry_waiting`，按退避时间重排。
- 重试期间该对话仍占用串行锁，避免同一对话并发跑两份任务。
- 达到上限后落 `failed`，并记录 `error_code` / `error_summary`。

**本次验收：`attemptCount = 1`，未触发重试。**

### 6.3 已知边界

| 项 | 状态 |
| --- | --- |
| 起草页前端**尚未**切换到任务订阅，仍走原 SSE 即时体验 | 已排期，非本次范围 |
| 仍是单进程原型，**未做多实例部署** | 已知边界 |
| `npm run lint` 不可用（缺 ESLint 9 flat config `eslint.config.js`） | 既有问题，不影响运行 |
| `test:word-annotations` 需本机安装 LibreOffice | 环境缺失，非代码回归 |
